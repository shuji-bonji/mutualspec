# ADR-0018: ライセンス: コード・スキーマ・ルール・サンプルは MIT、設計文書は CC BY 4.0

- 状態: Accepted
- 日付: 2026-11-19

## 状況

リポジトリには LICENSE が無く、ライセンスは未決だった（[13](../13-open-questions-and-risks.md) の Q-09）。LICENSE の無いリポジトリは、他者が読めても使えない。

決めるときに考えた事実は次のとおりである。

- 依存はいずれも MIT である（Ajv、remark、Mermaid、`@shuji-bonji/s1000d-core`）。s1kd-tools（GPL-3.0）は `validator: s1kd-tools` のときだけ外部コマンドとして呼ぶので、制約にならない（[ADR-0016](0016-s1000d-stack-as-default-validator.md)）。
- スキーマ、テンプレート、既定ルールセットの規則文（`use`）は、利用者の仕様ファイルと Context Pack に写される。ここに条件の強いライセンスを付けると、利用者の仕様そのものに条件が及ぶように読める。[01](../01-vision-and-principles.md) の「資産は Git に残す」という方針とも合わない。
- 所有者が npm で公開している他のパッケージ（rfcxml-mcp、pdf-reader-mcp、s1000d-core など）は MIT である。
- MutualSpec 自身をホスティングして収益を得る計画は無い。収益を得る部分があるとすれば、MutualSpec を使う別の製品やサービス（例: IETM / IETP エディター、顧客様式の定義、組織向けルールセット）であり、それらは中核の外に置く（[ADR-0017](0017-core-and-plugins.md)）。

## 決定

| 対象 | ライセンス |
|---|---|
| `schemas/`、`rules/`、`templates/`、`scripts/`、`examples/`（今後の実装コードを含む） | MIT（[LICENSE](../../LICENSE)） |
| `docs/`、`README.md` | CC BY 4.0（[docs/LICENSE](../LICENSE)） |

- 著作権表示は `Copyright (c) 2026 shuji-bonji` とする（既存の npm パッケージと同じ名義）。
- npm で公開するパッケージ（`mutualspec` と `@shuji-bonji/mutualspec-*`）の `license` は `MIT` とする。
- MutualSpec を使う別の製品やサービスのライセンスは、それぞれで決める。この決定はそれらを縛らない。
- 「当面」の決定である。著作権者が所有者だけの間は、将来の版を別のライセンスにできる。外部からの貢献を受け入れる前に、貢献の扱い（そのまま MIT で受けるか、同意書を求めるか）を決める。

## 検討した代替案

- Apache-2.0: 特許の許諾と、商標を許諾しないことを条文で明記している。名前の保護を重く見るなら有力だが、既存のパッケージと揃わず、NOTICE の扱いが増える。商標そのものの保護はライセンスではなく商標登録で行う（[13](../13-open-questions-and-risks.md) の R-08）。
- AGPL-3.0 / BSL: 他者がサービスとして提供することを制限できる。MutualSpec にはホスティングで守る収益が無く、形式が利用者のリポジトリに入るので、採用の妨げだけが残る。
- 全体を MIT にして文書を分けない: 管理は最も単純になる。設計文書を引用・翻訳するときに出典の表示を求めたいので、文書だけ CC BY 4.0 にした。
- サンプルを CC0 にする: 利用者が写しやすくなるが、ライセンスの種類が増える。MIT で足りる。

## 結果

- Q-09 は解決済みになった。
- 利用者は、スキーマ・テンプレート・既定ルール・サンプルを、著作権表示を残せば自分のリポジトリに写して使える。
- MIT の中核は、どのライセンスの製品からも取り込める。逆に、MutualSpec の MIT の部分へ AGPL-3.0 などのコードを取り込むことはしない。
- 商標（MutualSpec の名前）はこの決定の対象外で、未確認のままである。
